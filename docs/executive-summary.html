Why the “values in [0, 1]” error happens

A raw feature raster, fault-label nodata such as −1, infinity, an unmasked float32 sentinel (−3.4028234663852886e+38), or an unnormalized model output can violate the prediction range. The organizer's own reference solution strips exactly that sentinel (X_orig[X_orig < -1e38] = np.nan). Our writer rejects bad values rather than silently clipping them, and writes every pixel as a finite value in [0,1] with no nodata tag — the safest choice against the validator.

When a real candidate is approved for submission

  1. Check the readiness receipt. It must show a candidate SHA-256, successful format and novelty checks, feature-alone leakage canaries (AUC < 0.90), comparable pooled HOLDOUT-DTI with evaluator version, withheld-positive count and 95% CI, and separate selector approval.
  2. Download the named prediction. Use its unique .tif filename, or a ZIP containing exactly that one TIFF. Do not upload the JSON receipt, report, training data, or sample.
  3. Verify file integrity. Compare SHA-256 with the published receipt. Confirm exact CRS (EPSG:32611), dimensions, and geotransform against the organizer's real training_features.tif — do not rely only on the filename.
  4. Check the authenticated contest page. Read current eligibility, data rules, deadline, and remaining weekly cap at https://www.drivendata.org/competitions/306/competition-doe-gems/ . None of these is freshly verified in this environment.
  5. Use New submission. Choose the TIFF/ZIP in “File to submit.” Paste the published note (at most 140 characters). This site does not upload or consume slots for you.
  6. Preserve the receipt. Record the organizer's submission identifier, score, timestamp, and file hash. Only then label the result ORGANIZER-CONFIRMED. Rejection is not a successful submission.

What the H33 result (0.2778) likely means — and whether we can beat it

The owner-reported H33 value of 0.2778 is a self-reported internal simulation output, not an organizer-confirmed score. The GEMSDOE32 page itself states that no score in that repository is organizer-verified. The live public leaderboard (2026-10-21 snapshot) shows rank 1 at 0.4413, so 0.2778 is far from the current high.

From the pinned H33 bytes available to this project: 37,654 positive pixels, all off the mirrored catalogue, finite values in [0,1], matching CRS/shape/transform; median catalogue distance ~1,965 m; only ~5.8% of dots within 300 m of a mapped fault. The most plausible mechanism is metric efficiency under the distance-weighted Tversky index: sparse, well-placed dots maximize covered truth credit per emitted pixel while minimizing false-positive mass. A dot beyond the 300 m kernel radius contributes pure FP penalty; spreading the same total predicted mass thinly over a wide corridor can drop DTI from ~1.0 to ~0.22 even when total mass is identical (see docs/data/dti_mechanics_demo.json). Thinning a diffuse field to isolated high-credit dots is therefore a credible explanation for H33's relative performance — but causation is unproven, and the hidden evaluator's truth set is not public.

Can we score higher than 0.2778? Possibly — the live leaderboard already shows scores up to 0.4413 — but no result in this run establishes it. The path is: (1) obtain real competition data, (2) build a feature-only predictor, (3) pass the leakage canary (AUC < 0.90), (4) beat the current holdout best on identical spatial folds with pooled DTI + 95% CI, (5) pass the registry novelty gate (rank correlation < 0.90, < 70% of dots within 3 px of any prior), and (6) receive selector approval. None of these can be done without the real data currently behind DrivenData's login wall.
