Research: why does "thinning" score well, and can it be beaten?

evidence class: mixed The DTI formula and its behavior below are reproduced from the organizer's own published spec and independently computed with this repository's own code (scripts/demo_dti_mechanics.py → docs/data/dti_mechanics_demo.json). The specific sibling-repo number "0.2778" is a self-reported, non-organizer-verified claim — it is discussed here only as a motivating example of a general mechanism, never as a target to literally reproduce.

1. The metric, restated precisely

For α=0.2, β=0.8 and a 300 m (3-pixel) triangular kernel:

DTI = TP_w / (TP_w + 0.2·FP_w + 0.8·FN_w)

Two structural facts follow directly from the formula and matter more than any specific detector:

  • False positives are cheap, false negatives are expensive (0.2 vs 0.8): the metric is built to reward recall-seeking behavior over precision-seeking behavior, up to a point — see fact 2.
  • Credit is capped at the covering maximum, not summed: TPw for a given ground-truth pixel is a max over nearby predictions, not a sum. Piling multiple high-confidence predictions on top of the same truth pixel earns no more credit than the single best one — but every pixel of predicted mass that is not the arg-max for some truth pixel is pure, uncapped FP cost.

2. Why "thinning" (same geometry, less mass) raises DTI — a worked, reproducible example

We built a 60-pixel synthetic fault line and compared two predictions carrying the exact same total predicted probability mass (Σp = 60.0): (a) full confidence exactly on the true pixels ("thin"), and (b) the same total mass spread over a 5-pixel-wide corridor straddling the line at p=0.2 per pixel ("wide"). Computed directly by distance_weighted_tversky():

VariantTPwFPwFNwDTI
Thin (on-line, p=1)60.00.00.01.000
Wide (±2 px, p=0.2, same Σp)12.024.048.00.217

The mechanism is exactly the covering-maximum fact above: in the wide case, most of that spread mass sits 1-2 pixels off the true line. The triangular kernel discounts it (k(100 m)=2/3, k(200 m)=1/3), and — critically — only the single best-placed pixel per truth pixel counts toward TPw; the rest of the mass at other offsets from the same truth pixel is simply FP. This is the same qualitative effect several sibling repositories report finding empirically when "thinning a thick surface while keeping its geometry" raised their self-reported score — our result above derives it from the formula on a controlled synthetic case, independent of any of their claims.

Full reproducible output (JSON), including a third experiment on sub-pixel registration error: a systematic 1-pixel (100 m) offset of an otherwise perfect detector costs 1/3 of total DTI (1.000 → 0.667) in this synthetic case, and a 3-pixel offset (beyond kernel range) costs everything (→ 0.0). This is a quantitative version of the organizer's own warning that "rasterization is lossy and can induce off-by-one errors near pixel boundaries."

3. There is no universal "break-even credit per dot"

Some sibling repositories report a specific empirical constant (e.g. "break-even credit per dot ≈ 0.054") as if it were a property of the metric. It is not: it is a property of their specific candidate raster's TPw and FNw at the moment a new false-positive pixel is added. From the formula, adding one far-away false-positive pixel of mass p changes:

DTI_new = TP_w / (TP_w + 0.2·(FP_w + p) + 0.8·FN_w)

which is a function of the current TPw/FNw, not a fixed constant. We verified this closed form numerically (experiment_b_credit_density_breakeven in the demo JSON: adding one far false positive to a perfect 60-pixel prediction costs exactly 0.00332 DTI, matching the closed form to 1e-6). Anyone using a single "break-even" number across different candidate rasters is implicitly assuming their TPw/FNw stay constant, which is only true locally, around one specific operating point.

4. So — why did "0.2778" score higher than other sibling attempts, and can it be beaten?

Likely mechanism (consistent with the formula, not independently confirmed against the real raster): a buffer-pruning step that deletes predicted pixels within ~200 m of the known, pixel-exact-masked catalogue. This is independently justified by the organizer's own staff clarification (forum thread 11516, DrivenData staff, verified this session): known-fault pixels are excluded from scoring entirely, and predictions near but not on a known fault are not protected by any buffer — they are fully penalized unless they happen to land near a real new-fault pixel. Probability mass spent in that near-catalogue halo is disproportionately likely to be "wasted" (the obvious place to predict is exactly where a fault is already known to be, which is the one place that earns zero credit either way), so removing it raises the precision-of-remaining-mass and, by the mechanism in section 2, raises DTI per the same logic that makes thinning work.

Can it be beaten? Yes, in principle, two structurally different ways (not mutually exclusive):

  1. Reshape existing predicted mass (thin, deduplicate, prune near-catalogue halo) — bounded upside: this can only approach the DTI ceiling implied by whatever genuine detection signal is already present in the underlying field. It cannot discover a fault the field never encoded.
  2. Add genuinely new, independent evidence that is correlated with the held-out new-fault population specifically because it is not derivable from the same signals the public catalogue was built from. This is the only route with unbounded upside, and it is the one our four new hypotheses (H75-1..4) are built around: volcanic vent alignment, seismicity anisotropy, heat-flow×magnetic-depth conjunction, and slip-tendency azimuth mismatch — each drawn from a free, official dataset (GDR submission 1391 and linked USGS data releases) that, as far as we could verify against every sibling hypothesis list we could read, is not yet used by this project family in that specific way.

5. Why we are not reporting a number for "can we beat 0.2778 / 0.3195 / 0.4413"

Doing so honestly requires scoring a real candidate against the real catalogue on a spatially-blocked holdout. This project has not been able to access that catalogue this session (see Limitations). The mechanics above are real, reproducible, and falsifiable right now with synthetic data; the magnitude of their effect on the real GeoDAWN region is, honestly, unknown until the data blocker is resolved. We would rather publish that negative result than a fabricated one — see docs/data/run_card.json for the formal run card.
