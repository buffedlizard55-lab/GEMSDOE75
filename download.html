What must happen before this file can be submitted

  1. Get real data. A human with a DrivenData account downloads training_features.tif, labels.tif, and sample_submission.tif from the organizer's data page and places them in data/raw/. This sandbox cannot reach that login-walled page.
  2. Re-generate in REAL mode. Run python scripts/make_submission.py --rule fault_tip_halo so the template is derived from the real training_features.tif, not a placeholder.
  3. Validate geometry. Run python scripts/verify_submission.py docs/downloads/<name>.tif --template data/raw/training_features.tif to confirm exact CRS, shape, and transform match the organizer's grid.
  4. Run the holdout and canaries. Score the rule with gems_doe.holdout.run_holdout and leakage_canary against the real catalogue. Only a holdout DTI that beats the current best is eligible for a weekly slot.
  5. Check uniqueness. Compare against registry rasters (Spearman > 0.90 or >70% of dots within 3 px = duplicate, stop).
  6. Get selector approval. Promotion to a competition slot is a separate decision within the weekly cap shown on the submission page.

Why the “values in [0, 1]” error cannot happen with this file

The writer strips the documented float32 sentinel (−3.4028234663852886e38) and any NaN/inf, clips all values to [0,1], writes every pixel as finite (0.0 outside the footprint), and omits a nodata tag. The file is re-opened from disk and re-validated before the receipt is issued. Both documented mechanisms behind the portal error are closed by construction.
